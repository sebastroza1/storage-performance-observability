# Results and conclusions

Executed on 2026-10-29 with Python 3.12.14 on Windows 11 build 22631. The host
reported an AMD64 Family 23 Model 24 CPU and eight logical processors. The work
directory was on the 1.86 TiB C: filesystem, with approximately 977 GiB free.

## Validation summary

- 9 pytest tests passed in 0.41 seconds.
- The quick benchmark attempted 14,912 block operations: 14,912 succeeded and 0
  failed, for 100% availability **during this bounded run only**.
- `pip check` reported no broken requirements in the isolated virtual environment.
- `reports/results.json`, `reports/results.csv`, and `reports/benchmark.png` were
  generated by the committed code; the PNG was visually inspected.
- A real metrics process loaded the JSON and returned HTTP 200 from `/metrics`
  with Prometheus text format (11,649 bytes) on loopback port 8765.
- `docker compose config --quiet` was used for static Compose validation. The
  Docker daemon was unavailable, so Prometheus did not load the rules and neither
  alert was triggered. Both alerts are configured, not runtime-validated.

## Data-based conclusions

In this run, 1 MiB sequential reads showed the highest single-worker read
throughput, while 4 KiB random writes had the lowest throughput. Moving the
4 KiB random-read case from concurrency 1 to 4 did not improve aggregate
throughput (314.176 versus 312.203 MiB/s) and increased p95 block latency from
0.0160 to 0.0527 ms. That is evidence about this cached, Python-driven run—not a
general storage-device claim.

The four-worker 64 KiB sequential-write case reached 1,610.963 MiB/s, but it
changes both concurrency and block size relative to the single-worker write
cases. It cannot isolate concurrency as the cause. Sequential reads were faster
than comparable writes here, consistent with cache and synchronization effects,
but the benchmark does not measure direct device latency.

Disk free space was identical before and after at byte precision, confirming
fixture cleanup. The absence of errors is useful correctness evidence but is not
enough to establish reliability, an SLO, or long-term availability.

## Limitations and next experiment

Results are strongly influenced by the filesystem cache, OneDrive-backed path,
antivirus/background activity, Python overhead, and one final `fsync` per writer.
`fio` was unavailable, so direct I/O, queue depth, sustained writes, and explicit
cache invalidation were not tested. A regression study should repeat each case,
retain distributions over time, control host load, and compare against confidence
bounds on the same hardware.
